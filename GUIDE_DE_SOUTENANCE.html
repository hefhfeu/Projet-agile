1. Les Questions Classiques d'Architecture Logicielle

Question 1 : Pourquoi avoir choisi Django REST Framework et PostgreSQL plutôt qu'une solution NoSQL ou PHP ?
Réponse : Le modèle industriel d'une usine repose sur une forte cohérence relationnelle (17 entités hautement interconnectées : un incident doit appartenir à un lot précis, une maintenance est liée à une machine unique). PostgreSQL offre une gestion stricte des contraintes d'intégrité, des clés étrangères et des verrous de concurrence. Django REST Framework fournit un ORM puissant, un système de permissions RBAC natif et un back-office d'administration qui accélère la maintenance opérationnelle.
Question 2 : Comment garantissez-vous qu'un stock ne devienne jamais négatif lors d'interventions simultanées ?
Réponse : Dans l'application maintenance, l'enregistrement d'une consommation est enveloppé dans un bloc transactionnel atomique @transaction.atomic. Nous utilisons la directive SQL select_for_update() qui verrouille la ligne de la pièce dans PostgreSQL jusqu'à la fin de la transaction. Avant de décrémenter, nous validons :
if piece.quantiteStock < quantiteConsommee: raise ValidationError("Stock insuffisant").
Cela empêche tout accès concurrent incohérent (Race Condition).
Question 3 : Comment fonctionne l'algorithme de détection de cycle dans la nomenclature ?
Réponse : Dans apps/stock_achats/services.py, nous modélisons la nomenclature sous forme de Graphe Orienté Acyclique (DAG). Avant d'insérer un lien Parente → Composante, nous lançons un parcours en profondeur (DFS) à partir de la pièce composante. Si la pièce parente fait déjà partie de la descendance de la pièce composante, un cycle récursif infini se formerait : l'algorithme intercepte l'anomalie et rejette immédiatement l'opération avec une exception métier claire.
Question 4 : Comment le Frontend React communique-t-il avec l'API Django ?
Réponse : Le frontend utilise une architecture Single Page Application (SPA) asynchrone. L'authentification repose sur des jetons JWT (JSON Web Token). Lors du login, le backend délivre un access_token (courte durée) et un refresh_token. Chaque requête HTTP ultérieure injecte automatiquement l'en-tête standard Authorization: Bearer <token>. Si le token expire, notre client JavaScript tente un renouvellement transparent sans déconnecter l'opérateur.
